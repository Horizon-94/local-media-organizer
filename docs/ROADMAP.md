# Local Media Organizer 路线图

更新日期：2026-09-17

本页描述方向和验收条件，不是发布时间承诺。只有进入正式 Release、通过对应测试并提供可核验产物的能力，才算“已完成”。

## 当前公开基线

最新公开正式版本仍是 **1.2.7**：

- macOS Apple Silicon 原生应用；
- 原始素材只读，本地 SQLite 保存派生数据；
- 图片、视频画面、OCR、人物和人声转写的本地整理与搜索；
- 当前素材库和全部已登记素材库的统一查询；
- 文稿选片实验、人工主选/备选、JSON 清单与 FCPXML 粗剪交接；
- 应用携带运行环境但不携带模型、数据库、素材和用户配置。

维护者本地存在 1.2.8 候选验证记录，但没有作为 GitHub 正式版发布。已知未收口项包括事件级剪辑表的主体判断、一事件多镜头安排以及完整人工验收。公开说明必须继续区分“本地候选”和“正式 Release”。

## 近期：先把已有能力做稳

### 1. 搜索不阻塞前台

- 搜索过程中持续显示已确认结果，而不是等待全库结束后一次出现；
- 同一原视频的相邻画面按来源和时间窗口聚合，保留“浏览全部画面”；
- 画面、OCR、人声转写和人物搜索保持可解释的入口边界；
- 记录首个结果时间、最终排序时间、取消时间、峰值内存和磁盘读取，而不只报告总耗时；
- 最近查询可以即时恢复已保存结果，再异步刷新，但界面必须标明缓存与最新结果的区别。

### 2. 人物和采访/长内容

- 人物高置信分组和“待确认人物”都不能静默消失；
- 人工命名、合并、拆分和收藏必须跨应用升级保留；
- 对已有转写做时间连续片段合并、逐分钟整理、提问/回答线索与代表性原话；
- 所有总结都能回到来源视频和时间码，不确定说话人时保持未知。

### 3. 文稿选片从“相关”走向“可剪”

候选排序遵循：

```text
文稿在上下文中的任务
→ 可见事实边界
→ 主要视觉主体
→ 镜头职责
→ 技术与美学质量
→ 与前后镜头的重复、连续性和节奏
→ 人工决定
```

下一阶段重点：

- 正确处理否定、身份、心理、所有权、因果和时间关系，避免画面作过度证明；
- 一句或一个事件允许由建立、动作、细节、反应、结果等多个镜头共同覆盖；
- Excel 事件表的“时长预算”不得被误当成单个素材的剪点长度；
- KEEP_A_ROLL、同期声主导和素材缺口继续是一等结果；
- 使用跨题材人工 Golden Set 报告 Top-1、Top-3、缺口和 KEEP_A_ROLL 判断，不用单一项目规则冒充通用能力。

## 调度路线：从阶段串行到异构资源协同

“异步同构”或“同步异构”容易把三个不同问题混在一起。项目按下面三个维度描述，避免术语歧义。

### A. 当前：阶段串行，阶段内部同类并发

当前正式入口按阶段推进。一个阶段完成并提交状态后，下一个阶段才开始；抽帧、OCR、转写或模型分析可以在各自阶段内使用多个同类 worker。

优点是行为清楚、恢复简单、容易核对；缺点是上游已经完成一部分素材时，下游仍可能空等，硬件利用率也不均衡。

### B. 下一步：事件驱动异步交接

目标不是“所有阶段一起跑”，而是上游每完成一个可验证 item，就用短事务写入数据库；下游按依赖和资源预算领取已经就绪的 item，不必等待整个阶段结束。

必须先具备：

1. 统一的 task/item 状态合同与依赖图；
2. 原子领取、租约、心跳和幂等 execution key；
3. 有界队列和背压，避免抽帧速度远高于模型消费造成磁盘膨胀；
4. 暂停、恢复、重试、取消和孤儿进程回收；
5. 同一个 item 不重复写数据库，失败不能污染已完成结果；
6. 前台可见真实排队、运行、提交和失败状态。

### C. 后续：异构资源协同

CPU 解码、VideoToolbox、GPU/Neural Engine 推理、内存、SSD 和机械盘并非同一种资源。调度器需要同时考虑：

- 原始盘顺序读取优先，避免多个阶段对机械盘随机争抢；
- 抽帧和视觉模型之间设置缓存水位，而不是无限生成中间文件；
- OCR、Qwen-VL、Whisper、向量编码分别设独立并发上限；
- 前台搜索、播放和工程保存获得交互优先级；
- 内存、交换空间、磁盘延迟或模型退出达到阈值时只降并发，不静默扩大；
- 调度决策写入可审计日志，并能退回阶段串行模式；
- 串行与异步运行对同一输入产生一致的最终数据库结果。

因此，推荐的长期结构是：**异步的数据交接 + 有界的同类 worker 池 + 异构资源感知调度**。这比单独选择“异步同构”或“同步异构”更符合本项目的真实瓶颈。

## 不进入近期路线的事项

- 不自动下载或静默替换第三方模型；
- 不用新模型重跑全部历史素材作为普通升级步骤；
- 不以漂亮构图分替代事实、主体和剪辑价值；
- 不在缺少人工标签时宣称选片质量提升；
- 不把测试页面、诊断脚本或单一项目规则直接当正式产品能力；
- 不在未完成签名与公证前宣称无警告安装体验；
- 不把估算硬件性能写成实测结论。

## 发布闸门

每个正式版本至少回答：

1. 改了什么，哪些旧能力需要回归；
2. 是否修改数据库 Schema，是否提供兼容迁移；
3. 是否读取或修改原始素材、模型目录和用户数据；
4. 哪些自动测试、真实只读测试和人工验收已完成；
5. 安装包架构、签名、公证、SHA-256 和源码对应关系；
6. 哪些能力只是实验或候选，哪些是真正正式入口；
7. 已知失败和回退方法。
